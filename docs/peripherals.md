# 外设开发与接入

本文面向修改 Lisem 源码的贡献者，也作为 coding agent 实现外设时的工作入口。
开始前读取[根目录约定](../AGENTS.md)及[QEMU 约定](../qemu/AGENTS.md)，
核对工作区、子模块和已有改动。
器件行为由仓库中的代码实现；板型 JSON 选择已有模型、设置参数并描述接线，
不能通过导入 JSON 定义新的寄存器或协议行为。使用已有模型配置板型见
[自定义板型](boards.md)，构建与交付命令见[开发说明](development.md)。

## 确定实现范围

先查询与当前源码或候选包匹配的 `lisem board-models --model MODEL` 和
`lisem board-models --schema`，将 `MODEL` 换为目标型号，再阅读对应实现。
型号相似不等于协议兼容；器件能被识别，也不代表数据传输及全部工作模式
已经实现。

根据缺口选择修改层级：

| 缺口 | 修改位置与职责 |
| --- | --- |
| 已支持的器件，仅接线或参数不同 | 板型 JSON；保持固件实际配置与芯片路由一致 |
| 板外器件的命令、寄存器或信号行为缺失 | QEMU 独立器件模型及公共板级装配，配套 Rust 能力描述与校验 |
| 片内控制器、DMA、时钟或 PinMux 行为缺失 | QEMU 对应控制器和芯片适配层；不放进板外器件 |
| 器件需要宿主媒体、网络或其他外部数据 | 宿主数据通道及模型的输入输出接口；芯片侧仍经控制器执行 |
| 缺少可观察状态或操作入口 | 共享核心及相应前端；公共接口只暴露通用器件能力 |

先跟踪固件实际访问的控制器、总线、引脚和器件，定位断点后再扩展模型。
外部 SDK 和固件只作为只读依据与验证输入。不得修改固件规避缺口，也不能
通过宿主直接写业务结果、替固件调用驱动或伪造完成中断。

## 准备行为依据

结合器件手册、原理图、BOM、驱动调用和必要的真机观测，整理实现所需契约：

- 精确型号、硅片或协议版本、地址绑带，以及与已有型号的兼容依据。
- 寄存器地址和宽度、复位值、读写权限、保留位、W1C 与读清除等副作用。
- 总线事务边界、地址或命令阶段、重复起始、片选、字节顺序及错误应答。
- 使能、复位、上下拉、有效电平、输出驱动与释放状态，及中断锁存和屏蔽关系。
- 时钟来源、完成条件、FIFO/DMA 行为，以及忙、取消、复位和断开时的结果。
- 固件实际使用的模式、外部输入和可验收结果；尚无依据的行为单独列明。

在模型注释或测试中保留必要的手册版本、章节及推导依据，不把猜测写成硬件
事实。对尚未实现的模式使用协议允许的拒绝或明确诊断；保留位等行为按手册
处理。临时分析与测量放在忽略的 `artifacts/`，不提交私有手册、外部源码、
固件、凭据、日志或实例副本。

## 实现 QEMU 模型

模型代码放在按功能分类的 `qemu/hw/` 目录，公共声明放对应的
`qemu/include/hw/`。按硬件形态使用 I²C、SSI、qdev 或 SysBusDevice 等现有
接口，注册类型及生命周期；不要把一个独立器件硬编码进某款芯片的 SoC。
片内共用 IP 同样保持独立，由芯片适配层传入地址、IRQ、DMA 请求和时钟。

实现时逐项核对：

1. 定义状态、参数、总线回调及信号端口，区分数据传输、寄存器副作用和状态观察。
2. 让固件经片内控制器模型访问器件。中断由器件状态产生，再经实际连线送达
   控制器；DMA 由控制器及地址空间完成，保留访问权限和边界检查。
3. 延迟、去抖和完成事件按硬件条件在 `QEMU_CLOCK_VIRTUAL` 排程。读取状态
   不应为了等到结果而推进状态机，不用宿主 sleep 或读取次数制造完成。
4. 根据实际硬件分别处理复位、停钟、禁用和取消；取消未交付的事件及传输，
   保留已经发生的结果，不让旧定时器或回调作用到新一轮运行。
5. 明确释放定时器、通知回调、共享映射及其他拥有的资源。采集和传输有界，
   背压、溢出与丢失行为可观测，正常运行不持续写诊断文件。
6. 更新所属目录的 `meson.build`、`Kconfig` 及使用该模型的配置依赖，确认
   实际构建包含该类型。不要只修改 `.tools/` 或其他生成目录。

寄存器相似的不同代际只有在行为依据充分时才共享实现。参数表达真实可变
属性；固定协议版本属于模型身份，不做成可随意切换的运行参数。

## 接入能力目录、校验与板型装配

新增器件通常需要同时修改 Rust 与 QEMU。当前板型通过 Rust 校验并生成
检查后的装配计划，再由 QEMU 装配；公共模型目录不是动态插件加载器。
仅加入型号列表或 QEMU 类型注册都不足以完成接入。

| 位置 | 需要核对的内容 |
| --- | --- |
| [能力目录](../crates/core/src/board/models.rs) | `MODELS`、分类、端口、信号方向、数据接口、参数 schema 与示例、总线及组合约束、支持芯片 |
| [板型校验与编译](../crates/core/src/board.rs) | 参数类型、范围、必需接线、地址冲突、驱动冲突、合法路由、组合限制、装配计划及前端元数据 |
| [公共装配实现](../qemu/hw/core/listenai-board.c)与[声明](../qemu/include/hw/core/listenai-board.h) | 装配字段校验、创建器件、设置属性、连接总线、GPIO 与类型化数据接口 |
| `qemu/hw/riscv/arcs/`、`qemu/hw/riscv/venusa/` | 将芯片总线、控制器和焊盘路由接到公共装配层 |
| `boards/`、`chips/` | 实际板型选择和接线；仅在芯片能力或路由确实变化时调整芯片描述及对应实现 |

能力目录中的端口方向以器件为参照。引脚名、必需与可选端口、双向和开漏
行为必须与模型一致，数字量、电压和类型化数据接口不能互相冒充。更新
`signals`、`data_signals`、`interfaces`、`constraints` 等描述时，以真实支持
范围为准，不仅修改查询文案。

参数 schema 与运行时校验保持一致；未知模型、未知字段、未接必需端口、
地址冲突及未支持的连接应被拒绝。编译后的每个器件和网络都必须有实际用途，
不能为了让配置通过而跳过装配检查。新增模型也要进入装配覆盖检查。

内置板型与导入板型共用同一路径。板型只描述硬件连接，不能代固件设置
PinMux、打开控制器或补写寄存器。改变接线时，要同时验证旧路由不再传输，
新路由只有在固件实际启用后才生效。支持芯片列表不得超出已接入的路由能力。

需要新的用户操作或观察时，从共享核心增加状态或控制接口，再接入对应的
GUI、CLI、MCP 或 Python API；不要在某个前端另写一份器件状态。输入检查
实例、运行及操作身份，异步完成保留待确认与失败状态。参数与接口契约放在
各自文档，固件启动步骤、业务报文和业务断言放在对应测试工程。

## 参考已有的完整接入

HUSB320-BA 展示了一个 I²C 器件从目录到固件可访问链路的修改点：

- [器件模型](../qemu/hw/i2c/husb320.c)和[类型声明](../qemu/include/hw/i2c/husb320.h)：
  I²C 寄存器、初始化期限、CC/VBUS 状态、IRQ 与复位。
- [能力目录](../crates/core/src/board/models.rs)：`husb320-ba` 的端口、参数、
  `partner` 数据连接和使用约束；[板型编译](../crates/core/src/board.rs)将其
  转换为装配计划中的 `typec`。
- [公共装配](../qemu/hw/core/listenai-board.c)：`listenai_board_load` 读取计划，
  `listenai_board_attach_typec` 创建并连接器件；芯片侧提供实际 I²C 总线与路由。
- [I²C 构建列表](../qemu/hw/i2c/meson.build)和
  [公共装配配置](../qemu/hw/core/Kconfig)：将器件纳入构建依赖。
- [Arcs-Mini3](../boards/arcs-mini3.json)和
  [模型回归](../tests/run_qemu_typec.py)：分别说明板级接线和跨芯片验证。

参考其分层与验证方式，不照搬该器件的单实例限制、地址、期限或引脚语义。
若新增器件允许多个实例，目录、校验、装配和测试都要覆盖独立状态及地址隔离。

## 宿主数据通道

需要宿主输入输出时，将宿主服务或传输适配与芯片、器件模型分开。参考已有
音频、摄像头和网络通道，先定义数据单位、方向、格式、容量、背压、时间戳、
身份确认和断开语义，再接入模型。高频数据不逐帧或逐包走 QMP，不在宿主
采集回调等待 UI 或执行器件逻辑。

外部来源仅提供实际数据和信号；固件仍经相应控制器、FIFO、DMA 和 IRQ
完成访问。虚拟时刻与宿主采集时刻分别记录，明确两者的映射及超限行为，
不能把宿主返回成功直接解释为固件操作完成。宿主接口不支持的模式明确报告。
新增宿主组件须随原生包分发，验证平台权限、断开、退出释放和包迁移后的运行。

## 验证顺序与交付

验证分为配置、模型、运行接口和固件业务四层，不能相互替代。按实际修改
选择相关单项，再执行受影响范围的完整回归；具体命令与平台要求见
[构建与维护](development.md)。

1. **目录和配置**：为新增 schema、目录详情及装配计划补测试，覆盖有效参数、
   未知字段、边界值、缺线、错线、冲突和未支持芯片。使用 `make test-core`
   验证共享核心，确认内置与导入描述得到等价装配。
2. **器件和控制器**：在 `tests/` 增加有界的模型回归，验证实际总线收发、
   数据字节、状态、IRQ、时间边界，以及复位、取消和失败路径。参考
   [板型装配回归](../tests/run_qemu_board.py)与器件专项；HUSB320 对应
   `make qemu-typec`。新增专项接入 `Makefile` 的 `QEMU_TESTS`，让
   `make check-qemu` 包含它。调试探针不能替代原固件验证。
3. **产品入口**：重建包含本次改动的原生包，确认 CLI、worker 与 QEMU 身份。
   用该包查询模型与 schema，校验、导入独立 ID 板型并创建独立实例。核对
   新增控制和观察路径、过期请求拒绝、重复操作、断开清理及资源所有权。
4. **原固件行为**：使用原始 LPK，按正常启动与操作流程验证实际功能。
   识别寄存器通过、DMA 字节正确、画面或音频输出、业务完成分别记录。
   验证受影响的已有板型和芯片，检查 Flash、OTP 与 UID 保持及实例隔离。
   缺少目标固件或真实外部条件时，明确保留未验证范围。

测试使用独立设备库、明确宿主期限与虚拟时间或指令上限，失败保留原异常和
必要证据。原始 UART、截图、数据和信号轨迹按需显式采集，不放宽断言追求
通过。配置校验、型号识别和宿主连接均不单独证明业务完成。

修改宿主组件或打包后，按各目标平台验证原生包迁出源码目录及屏蔽开发依赖
后的实际运行；平台结果分别报告。仅改模型文档时检查内容与引用，无需因此
重跑产品测试。

交付说明包含支持的型号与模式、实现依据、板型接线、运行前置条件、实际
验证范围和未支持行为。保持分组件许可，不提交外部输入与生成物。
QEMU 与父仓库分别组织完整逻辑提交；获得推送授权后先发布 QEMU 提交，
再更新父仓库 gitlink。不得让父仓库引用未发布的 QEMU 提交，或以本地包
冒充正式 CI 发布产物。
