# 架构与兼容性

## 层次

设备实例持有 Flash、OTP 和设备元数据。UID 位于 OTP，Flash 擦除或 LPK
导入不会改变身份。板型指定芯片、屏幕、外部存储和引脚交互；LS2684 芯片
包含 AP/CP、控制器、片内 Codec、LUNA 和 PinMux。芯片模型不实现应用业务。

QEMU 上游版本由 `tools/build_qemu.py` 固定并校验；`qemu/` 是源码覆盖层，
`patches/qemu-n300.patch` 保存上游改动。两核以串行时间片执行，LUNA 在
宿主计算，结果在虚拟完成事件写回。未实现的寄存器或模式明确报错。

`crates/core` 是与前端无关的 Rust 核心，管理硬件描述、实例库、LPK、
Flash/OTP、运行生命周期及控制协议。GPUI 和 `lisem` CLI 共用它；无头构建
不链接窗口系统，也不自动打开宿主音频设备。

每个活动实例由一个独立 Rust worker 管理 QEMU、存储锁与宿主连接。
`run` 是前台所有者，收到中断时停止该轮运行；`start` 将运行留在后台，
允许后续 CLI 或 GUI 连接。关闭窗口和退出 GUI 保留后台运行及 UART 端点；
显式下电停止 QEMU，`shutdown` 关闭实例运行时。控制请求使用实例身份和运行路径拒绝过期输入。

控制端点使用回环 TCP 和随机令牌，端点元数据保存在实例目录；QMP、三路
UART 分别有独立连接，串口转发不依赖 UI 轮询。音视频不通过 JSON 传递。
POSIX 上 QEMU 继承同一存储锁的文件描述符，控制进程异常退出也不能让其它
客户端在 QEMU 尚未退出时覆盖 Flash。Windows 使用禁止共享的文件句柄，
经 QEMU 的闲置标准输入继承，避免父进程退出释放存储保护。

芯片和板型的启动适配集中在后端 provider，当前只注册 LS2684 + Arcs-Mini。
增加芯片时复用 QEMU 器件/IP 类型，由 SoC 实现内存映射、时钟和中断连接；
增加板型时定义器件与总线/引脚连接及外部交互。Rust 前端仅消费描述和能力，
不能用修改 JSON 代替尚未实现的芯片、器件或连线模型。

板型通过 `indicators` 声明指示信号的引脚、有效电平和显示属性。桌面在
顶栏以圆点显示 LED 和信号指示器，功放使能映射到声音图标的点亮状态；
宿主静音单独控制。圆点在信号有效时高亮，悬浮提示统一显示名称及有效、
无效、未驱动或下电状态。指示器只观察引脚，不修改电平，也不
参与实例的硬件连接匹配；改变观测点或呈现方式不影响 Flash、OTP 和连线。

平台接口与通用核心分开：共享内存在 POSIX 使用 `shm_open` 和 `mmap`，Windows 使用
`CreateFileMapping`；原子帧和 PCM 布局相同。UART 在 POSIX 暴露 PTY，
Windows 暴露回环 TCP 原始字节端点，不依赖虚拟 COM 驱动。后台进程不打开
额外控制台，调用方的标准管道不会泄漏给长期运行的后代进程。

## 显示

屏幕器件使用 QEMU 的 `QemuConsole`、`DisplaySurface` 和更新通知。
独立 DisplayChangeListener 以约 60 Hz 请求刷新，仅在像素变化时发布
BGRA 帧；三个共享槽通过原子所有权交接，生产者不等待消费者。

Rust 独立线程读取最新帧，GPUI 按刷新周期更新纹理。状态轮询不限制画面
刷新率；隐藏或繁忙窗口不会让历史画面排队。当前固定分辨率的 CPU 帧有
一次复制和纹理上传，240×240 时每帧约 225 KiB；无需引入视频编码。
正常运行不创建运行归档。画面、音频和 UART 使用有界内存缓冲；
截图由用户显式导出，诊断录制由 CLI 的 `--capture` 启用。

这种分离控制与图像、使用更新通知及共享缓冲的方式，与
[QEMU D-Bus 显示接口](https://www.qemu.org/docs/master/interop/dbus-display.html)
提供的共享映射及局部更新原则一致。当前使用直接共享映射连接 GPUI，
未实现 D-Bus、SPICE 或虚拟 GPU 协议，也不声称 GPU 零复制。

## 音频

片内 Codec 仍按原采样事件处理 FIFO/DMA。板级端点记录 PCM、虚拟时间戳
和 PA 状态，经有界共享环连接宿主音频端点。宿主输出连续运行，麦克风
独立启用；关闭麦克风无需申请录音权限，并可使用文件作为 ADC 输入。

APC RX0 接 ADC，RX1 可选择 TX0 的片内数字回采，支持独立左右声道、
单声道/交织 FIFO 与 DMA。数字回采在 Codec 静音及板级 PA 之前取样，
与 MIC1 电参考互相独立；未实现的 I²S 输入和 SRC 降采样明确拒绝。

首次 ADC/DAC 事件建立音频的宿主时间起点，只调整后续节拍等待；不改变
虚拟时间、指令预算或采样事件。启动前的 CPU 耗时不成为永久播放积压。
麦克风保留 250 ms 输入余量，以吸收宿主回调调度波动，缺样仍明确计数。
实时输入通过消费游标交给 ADC；缺样时插入计数的静音，补足 250 ms 后继续，
游标不越过已采集的数据。积压超过 500 ms 时，消费者将 MIC 与 AEC 参考
一起移到最近的 250 ms 窗口；长时间停顿导致环满时，生产者拒收新块，不覆盖
消费者拥有的数据。
`input_skipped_frames`、`input_dropped_frames` 与 `input_resyncs` 分别记录跳过的
旧输入、拒收的新输入和重新对齐次数，并通过运行状态及最终报告公开。
这会造成可观测的输入缺口，不能视为无损采集或实时性能达标。
`--capture` 诊断录制不采用此策略，缓冲耗尽仍报告失败。

宿主回调只操作内存及原生音频队列；文件写入、控制和进程管理由普通线程处理。队列采用
10 ms 缓冲，首次播放等待 80 ms 预缓冲，从第一份 DAC 样本开始，而不是从 CPU
上电开始。启动前无 DAC 的时间不构成音频欠载；开始后保留全部样本、静音
及虚拟时间间隔。PA 和宿主静音仅作用于实际播放，原始记录不改写。

DAC 数据迟到时插入可观测的宿主静音，不前移原 PCM 游标；后续样本仍保留。
因此 CPU 暂时跟不上时可能形成积压，不能靠剪掉静音或丢样把它伪装为实时。
报告包含 ADC 缺样、输出欠载、队列峰值和双方错误。下电是主动取消播放，
与正常预算结束后的队列排空分别记录。

[QEMU 音频后端](https://www.qemu.org/docs/master/system/invocation.html)
将虚拟声卡与宿主后端分离，其 CoreAudio 后端目前仅支持播放。
macOS 使用 [Apple AudioQueue](https://developer.apple.com/library/archive/documentation/MusicAudio/Conceptual/AudioQueueProgrammingGuide/AboutAudioQueues/AboutAudioQueues.html)
承担双向原生音频；Windows 使用 PortAudio 的 WASAPI 共享模式，Linux
直接连接 PulseAudio 协议（兼容 PipeWire 的 pulse 服务）。不使用 UI 轮询
或分段播放器。Windows/Linux 端点在独立音频线程中处理 PCM；Linux 使用
服务器提供的录放延迟，Windows 使用 WASAPI 回调时间戳对齐 AEC 参考。
当前桥接固定为 16 kHz
单声道 PCM16；芯片模型支持的其它采样率不等于宿主桥接也已支持。

### Mini 的 AEC 回采

Mini 的 MIC0 接麦克风，MIC1 接功放后 SPK+/SPK− 的分压/滤波回采。
板级模型向第二路 ADC 提供归一化电参考，PA 关闭时为零；经原 Codec、
APC 与 DMA 交给固件，不替代固件的 AEC 算法。当前不模拟模拟增益、RC
频响或扬声器失真，也不向麦克风凭空叠加室内回声。

离线单声道输入的参考取严格早于 ADC 边沿的 DAC 样本；停止输出后不重复
陈旧样本。双声道测试文件可提供独立录制的 MIC0/MIC1。
连续麦克风使用宿主音频接口的播放时间戳，将已经排定播放的 PA 后 PCM
与麦克风采样对齐，再一起送入 ADC。原始麦克风、参考和 DAC 分别保留。
宿主录放回调交错时，麦克风样本在有界队列中等待对应的 DAC 参考；不会
用重复样本替代尚未产生的参考。队列溢出明确报错，等待量记录在音频报告中。
宿主静音不改写模拟板的电参考或原始 DAC。实际声学效果受宿主扬声器、
麦克风及环境影响；双讲和播音中唤醒的验证要求见[开发说明](development.md)。

## 存储、串口与网络

- ROM 是构建时链接的固定 AP 64 KiB、CP 32 KiB 资产，不可擦除或替换。
  正常上电执行 ROM；暖复位保留 Flash 的实际擦写结果。
- Mini 的 CS0 接 16 MiB NOR，CS1 无器件返回 `0xFF`。PSRAM 为片内封装的
  128 Mbit 器件。NOR 写回失效两核代码缓存；OTP 独立持久化。
- LPK 在宿主解析后按包内偏移写入 Flash；串口烧录另经真实 ROM、RAM
  Loader、UART FIFO 和 CPDMA，不由宿主解析协议或伪造返回。
- cskburn 流式回读（`CMD_READ_FLASH_STREAM`）存在超时问题。
- macOS PTY 不支持 DTR/RTS。Mini 的 BOOT/RESET 连线用桌面“复位到烧录
  模式”进入；烧录工具选择不复位策略。串口原始字节不改写换行或脱敏。
- UART 宿主端点属于实例，复位或上下电不更换；关闭所属 worker 或禁用端口才关闭。
  重新打开应用恢复启用状态，系统分配的路径可能变化。
- Wi-Fi 使用板级逻辑 AP，libslirp 提供可选宿主上联。固件自行完成 DHCP、
  TLS、鉴权和业务；默认 CLI 不连接公网。BLE 当前为逻辑报文对端，尚无
  真手机宿主桥接。SD 和 USB 不制造数据或成功事件。

## 摄像头

Mini 的 GC0328 通过标准 QEMU I²C 总线连接 I2C0；SCCB 的 PB6/PB7
复用及 PA26 摄像头时钟输出必须由固件配置。I²C 主模式按配置的总线时钟
逐字节执行，8 字节 FIFO 满／空时等待软件搬运，支持 ACK/NACK、事务完成
中断和 W1C。控制器命令复位终止事务、清状态和 FIFO，保留时序配置；
模块复位恢复寄存器初值。DMA、从模式和 10 位地址尚不支持。

GC0328 的独立器件模型保留分页寄存器、只读芯片 ID 和软件复位；输入场景
与传感器复位分离。宿主图片在 Rust 内有界解码、居中裁剪为 640×480 RGB888，
通过有界共享内存交给板级适配器；像素和裁剪寄存器在帧开始时锁存。支持窗口、翻转、
RGB565、四种 YUV422 排列及输出字节交换。图片代表理想校准后的场景，YUV
采用全范围 BT.601 和成对平均色度；不模拟镜头、模拟 ISP、自动曝光或颜色调校。
未选择图片或传感器关闭输出时接收器等待，不能制造 SOF、像素或完成事件。

输入源与传感器分离，固定三个 640×480 RGB888 槽使用跨进程原子所有权；
读取元数据和像素均须持有槽，正常运行不写媒体文件。QMP 仅确认源代际的选择
或清除，连续帧通过共享内存发布，不逐帧请求 QMP。待确认新源的首帧固定保留，
旧源仍可使用另两个槽；选择失败继续旧源，超时不重试或提前宣称成功。
接收器按所选代际取最新完整帧，SOF 锁存后整帧不可变；宿主过快允许丢旧帧，
分别统计生产端无空槽丢弃和未被 SOF 采样的帧。静态源可一直重复，连接中的
实时源过慢可复用最后场景，并报告重复次数、接收／采样序号及宿主时间戳。
显式断开或清除后不再产生新传感器帧，已锁存的帧仍可结束；重连唤醒等待中的
接收器，传感器复位保留外部场景。连续发布协议已有回归，当前产品界面仅接入
静态文件，尚未实现宿主摄像头采集。

Mini 的 PA10..20 连接同步信号和 DVP D[4..11]，因此接收器使用 LEFT 对齐。
DVP 独立维护窗口、16 个 32 位字的 FIFO、阈值、IRQ/W1C 和取消；CPU 读取
FIFO 只窥视首字，GPDMA 请求 5 的 32 位八字突发确认才弹出数据。支持输入格式
0/1/2/3 的双字节像素和 RAW8 的字节窗口，这些模式不额外重排传感器字节。
静态 FIFO 产生一次突发请求；后续输入重新触发请求，阈值不改变 FIFO 容量。
溢出记录状态并丢弃新字；完整溢出恢复及其他 DMA 突发模式尚未校准，后者明确拒绝。

SOF 和接收窗口 EOF 分别由虚拟事件产生，DMA 完成不替代 EOF。输入保持
逐字到达的虚拟时刻，但只在首字、阈值、满／溢出、行尾等可见边界排定事件；
CPU 窥视、寄存器访问、DMA 和取消前补齐已经到达的字。尚未到时的数据不会
提前进入 FIFO 或 RAM，DMA 仍在原有服务事件写内存；输入和 DMA 同刻时
保留原先的排队顺序。
事件依据功能时钟及传感器行周期排程，保留消隐阶段。VSYNC 以同步脉冲结束的
帧边沿启动；PCLK 两种采样边沿相差半周期，传感器反相交换采样相位。该功能
时序不宣称精确复现硅片传播延迟。
禁用时钟或复位取消采集，恢复输入会唤醒等待中的接收器。采集中丢失引脚复用或
改变 MCLK 分频明确拒绝。其他位宽、右对齐、缩采样和测试图案仍明确拒绝。
传感器识别、控制层初始化、实际像素 DMA 及原业务拍照是不同的验证层次。

## 时间模型与边界

桌面使用 HCLK 功能时钟与宿主节拍同步：限制模拟器超前，不跳过指令、不
改变外设事件。暂停排除在宿主活动时间外，暖复位保持时间轴。HCLK 模型
按每条指令一个周期计数，不模拟物理缓存和流水线时延。
桌面双核轮转上限为 10 µs；任一运行核的 ECLIC 屏蔽阈值非零时，细化到
最多 1 µs，入口先结束当前时间片，让落后的核追上，再执行临界区代码。
ECLIC 每次输入仍更新电平和边沿锁存，仅 pending 改变时重做中断仲裁；
软件清除 pending 后的有效电平重断言、配置修改及陷入返回仍即时生效。
两核均处于 WFI 且没有调试、停止、复位或待处理 CPU 工作时，TCG 线程可直接
推进到原有最早虚拟事件，并回到正常定时器处理入口；每轮释放 BQL。该路径
不增加指令或跳过外设事件，保持宿主节拍限制，并以次数和宿主耗时限制连续
本地推进，定期返回主循环服务 UART、网络、控制请求和实时定时器。其他
AioContext 的到期事件、单步和禁用的虚拟时钟沿原有等待路径处理。
这可避免遗漏共享 RAM 中较短的恢复信号；不调整核频率、累计指令数或
外设截止时间，也不检查固件地址或握手内容。

LUNA 保留已表征的原微程序 ABI、整数舍入/溢出和完成边界；不认识的 ABI
拒绝执行。当前硬件分层支持既有 Mini，尚未实现任意换板或迁移快照。

## JPEG 解码

ARCS JPEG 控制器接收固件写入的量化表、规范 Huffman 表和 ECS 压缩数据，
通过 GPDMA 请求 6/7 交付 MCU 块。支持基线灰度、YUV444、YUV422 和 YUV420；
宿主 libjpeg-turbo 执行整数 IDCT，固件仍负责 JPEG 文件解析、色彩转换和显示。
完成事件在虚拟时钟上按 MCU 数量调度，时钟门控暂停处理，STOP 和复位取消
尚未完成的处理；结果通过像素 FIFO 读取，完成中断保持 W1C 和掩码语义。
功能时延不代表硅片逐周期时序。编码、缩放、RGB 输出和扩展 DMA 模式尚不支持。
